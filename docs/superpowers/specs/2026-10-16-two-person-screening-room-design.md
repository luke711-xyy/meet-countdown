# 双人在线放映室：第一版设计

## 目标与边界

在现有「见面倒计时」双人房间内增加一个低打扰的放映入口。房间任一成员可以主动共享自己的浏览器标签页、窗口或屏幕；另一成员实时观看；双方可以实时语音对话和发送短弹幕。两个成员都能发起“暂停/继续”的请求，分享者收到请求后操作外部播放器并确认。第一版不声称网页能远程控制任意外部播放器，也不录制或保存屏幕、通话和弹幕。

这延续此前已确认的第一版范围。同步播放同一个视频文件（真正的双端播放、暂停和进度同步）属于后续独立模式，不混入屏幕共享模式。

## 方案选择

采用浏览器原生 `getDisplayMedia`、`getUserMedia` 和一对一 `RTCPeerConnection`。已有 Cloudflare Worker + `CoupleRoom` Durable Object 的鉴权 WebSocket 负责入场、信令、弹幕和控制消息；媒体优先点对点直连，连接失败时使用 Cloudflare Realtime TURN。选择这种方案是因为房间始终只有两个人、UI 要保持现有风格，且逐帧视频不应进入 Worker、D1、R2 或现有 Three.js 渲染循环。

不选 Worker WebSocket 转发视频：它不是媒体服务器，会增加带宽、延迟和故障面。不在第一版引入 SFU：两人连接并不需要额外的媒体路由；若以后支持多人或复杂跨端订阅，再评估 Cloudflare Realtime SFU。也不把视频逐帧绘入现有水波纹画布。

## 用户流程与界面

1. 登录并进入已有双人房间后，顶栏设置按钮旁出现放映入口，沿用小尺寸白色描边图标、透明毛玻璃背景和现有悬浮球反馈。入口有文字/无障碍名称「进入放映室」，图标采用简约屏幕轮廓，不增添说明性标语。
2. 点击入口进入覆盖式放映界面。未有人共享时，两人都能看到一个「共享画面」主操作；点击时由浏览器提示选择捕获源。页面不会自动申请屏幕或麦克风权限。有人共享时，视频居中等比显示，黑边仅留在视频容器内；当前共享者的身份和连接状态可见。
3. 底部自动出现一组与侧边悬浮球一致的玻璃圆形控件：麦克风开关、弹幕输入、暂停/继续请求、共享/停止共享、离开放映室。鼠标或触控操作都可显露控件；空闲时弱化，但键盘焦点仍可见。弹幕只浮过视频上方，不遮住关键控制。
4. 分享者点击暂停/继续时，界面提示其操作外部播放器，并由分享者确认“已暂停/已继续”；观看者点击时发送请求，等待分享者确认。双方看到同一请求和确认状态。不提供会导致画面冻结但原片继续播放的伪暂停。
5. 任意一方离开时，通话和屏幕连接关闭；另一方留在放映室等待或退出。房间被销毁则双方立即退出。录音留言、任务与倒计时原有数据不受放映室临时状态影响。

布局的主角始终是视频；桌面端控制位于视频下方，手机端采用底部安全区内的紧凑排列。保留现有浅/深文字主题、系统字体、毛玻璃材质和键盘焦点样式。`prefers-reduced-motion` 下弹幕只淡入淡出，不横穿画面。放映中暂停或明显降低背景水波纹与涂鸦的渲染工作，避免与视频解码争抢资源。

## 客户端分层

- 保持现有 DOM 页面为 UI 真值源；放映室使用普通语义 DOM 叠层，视频用原生 `<video>`，弹幕与浮球用 DOM/CSS。这是 `html-in-canvas-frontend` 的 `overlay` 模式：视频、文字和按钮都不需要投射到 Three.js 纹理。
- 放映模块与倒计时、录音、任务、涂鸦模块分离；只通过现有房间会话、身份信息和主题变量连接。模块拥有媒体轨道、PeerConnection、设备权限、入场/离场与清理生命周期。
- 使用特性检测决定是否提供共享按钮；不支持 `getDisplayMedia` 的设备仍可观看、发弹幕与尝试语音。移动端必须以实际目标浏览器测试，不能只按 UA 推断功能。

## 信令、权限与状态

- Worker 的 `/ws` 已验证登录态和房间成员资格；扩展 `CoupleRoom.webSocketMessage`，只允许两个房间成员交换限定类型和大小的 `screening.*` 消息。信令包括 join/leave、offer/answer/ICE、共享状态、暂停请求与确认、弹幕。发送者身份由 WebSocket 附件得出，不能信任客户端传来的成员 ID。
- 每次放映生成独立 `sessionId`，每条控制消息包含会话和递增序号；旧连接、重连前的 ICE 候选、重复暂停确认均被忽略。信令定向发送给另一成员的放映设备，而不是向同账号所有打开的标签页广播。
- 同一账号多端打开时，一个放映设备处于活跃状态；另一设备可提示“正在另一设备放映”并主动接管，接管时旧连接和媒体轨道被清理。房间同一时刻最多一个屏幕共享者；对方可以在前者停止后接续共享。
- 弹幕限制长度、发送频率与同屏条数；仅在房间会话中短暂显示，不写入 D1。恶意或过大的 SDP/ICE/弹幕消息必须被拒绝。断开、超时或房间销毁后清理临时状态。
- TURN 长期密钥只保存在 Worker secret；后端仅向已认证、已入房的用户签发短期 ICE 凭证，不向浏览器暴露长期密钥。默认不录制媒体。

## 媒体与质量策略

- 分享者的视频轨道和可用的标签页音频来自 `getDisplayMedia`；双方麦克风分别来自 `getUserMedia`。麦克风启用浏览器支持的回声消除、降噪和自动增益，并优先建议耳机。若浏览器没有提供所选来源的音频轨道，界面明确显示“未共享影片声音”，不能假装已共享。
- 起始目标为 1080p/30 fps；设备或网络受限时优先退到 720p/30 fps。60 fps 只作可选增强，不构成验收承诺。浏览器协商媒体编码；屏幕里主要是影片时可给视频轨道 `contentHint = 'motion'`，但实际支持和效果由浏览器决定。
- 每 2–5 秒从 WebRTC stats 读取实际发送/接收帧率、分辨率、丢帧、丢包、抖动、RTT 和当前候选路径；持续恶化时逐级降低视频码率/分辨率，恢复稳定后缓慢上调。语音连续性优先于画面清晰度。UI 可显示简短的连接状态，不展示冗长诊断文字。
- ICE 断开时尝试受限次数的 ICE restart；无法恢复时明确提示重新加入。浏览器停止共享或关闭页面时立即停止轨道并通知对方。音频自动播放被浏览器限制时提供一次明确的“开启声音”操作。

## 实施范围与验证

预计修改 `public/index.html`、`public/styles.css`、`public/app.js`，新增独立客户端放映模块，并扩展 `src/worker.ts` 的信令与短期 TURN 凭证接口；按需增加针对信令鉴权、状态机和消息校验的测试。无需 D1 迁移或 R2 媒体存储。先在本地完成两真实浏览器/设备的互通验证，再决定生产部署。

验收需覆盖：双方轮流发起共享；标签页音频存在与不存在；双向语音、静音与回声；弹幕发送、限流和低干扰显示；暂停请求—分享者确认的双端状态；一人断线/重连/关闭页面、房间销毁；同账号多端接管；STUN 直连与强制 TURN 中继；桌面和手机观看布局；键盘、触控与减弱动态效果。通过统计和真实画面证明实际帧率/清晰度与通话连贯性，不能只凭编译通过宣称完成。

## 明确不做

第一版不提供远程操作对方电脑、控制任意第三方播放器、绕过受保护内容的屏幕捕获限制、云端录像、历史弹幕或多人放映。对于版权保护的视频来源，捕获可能出现黑屏或无声，应诚实提示并使用双方各自合法观看的方式。
